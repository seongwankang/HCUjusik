# 과거 기록 재사용과 증분 조회

Firestore Standard/Spark와 기존 GitHub Pages 구조를 유지한다. 별도 서버나 유료 서비스는 추가하지 않는다.

| 데이터 | 조회 방식 |
| --- | --- |
| 내 체결 기록·투자/고용 이력·확정 이벤트 적용 기록 | 최초 조회 후 보관하고 새 기록만 합침 |
| 차트 체결 자료 | 최근 100건 보관, 새 체결이 생길 때 추가 |
| 배당·산업스파이 정산 이력 | 최근 30건 보관, 이후 증분 조회 |
| 변경할 수 없는 이벤트 정의 | 최초 조회 후 새 이벤트 추가 |
| 현금·보유 주식·호가·미체결 주문·회원 권한·기업 설정 | 기존 방식으로 최신 조회 및 트랜잭션 검증 |
| 수정/삭제 가능한 뉴스·댓글·진행 중인 정산 | 이 캐시에 보관하지 않음 |

## 저장과 갱신

`client/immutable-reader.js`는 문서 ID로 중복을 제거하고, 모든 페이지를 성공적으로 읽은 다음에만 최신 조회 위치를 갱신한다. 계좌 버전, 마지막 투자/이벤트 ID 등이 같으면 과거 기록 조회를 생략한다. 변경을 알려주는 버전이 없으면 마지막 시각 이상(`>=`)만 읽는다. 같은 시각에 생성된 기록을 놓치지 않기 위해 경계의 일부 기록은 다시 읽을 수 있다. Timestamp의 나노초 정밀도도 보존한다.

표시용 기록은 프로젝트별 IndexedDB에 현재 Firebase UID와 함께 저장하므로 새로고침 후에도 재사용한다. 계정 변경·로그아웃 시 메모리와 저장소를 비운다. 이전 계정에서 시작한 늦은 응답은 새 계정의 저장소에 기록하지 않는다. IndexedDB가 없거나 용량/비공개 모드로 실패하면 메모리 캐시로 동작한다. 비밀번호·토큰·권한·현재 잔액은 저장하지 않는다.

표시 캐시를 정산의 근거로 신뢰하지 않는다. 재무 처리용 이벤트 조회는 별도 메모리 리더를 사용하고, 실제 거래와 정산의 최신 문서 확인 및 Firestore 트랜잭션/규칙은 유지한다. API의 회원 상태와 접근 권한 확인도 계속 수행한다.

## 화면 처리

거래창의 경영/배당 요약은 경영이력 전체 조회를 기다리지 않는다. 경영이력이 화면에 보일 때 읽기를 시작하고 스크롤할 때 20개씩 화면에 붙인다. 시세 갱신 시 기존 이력 목록과 스크롤을 유지한다. 오래된 손실금 기록도 누락하지 않는다. 같은 체결 자료로 차트를 반복해서 그리지 않는다.

처음 사용하는 기기에서는 평균 매입가 계산에 필요한 전체 체결 기록이나 경영이력의 과거 투자 자료를 한 번 읽어야 한다. 경영이력의 20개 단위는 화면 페이지 크기이며, 최초 Firestore 읽기가 20건으로 제한된다는 뜻은 아니다. 이후에는 저장한 자료와 새 기록을 합친다. 최초 조회 시간과 현재 데이터의 네트워크 지연은 남는다.

## 운영과 검증

이 방식은 기존 규칙이 변경/삭제를 금지하는 기록만 대상으로 한다. 관리자가 콘솔로 과거 기록을 수정·삭제·역시각 추가하거나 행사를 초기화하면 이 가정이 깨진다. 이 경우 로그아웃 후 재로그인하여 기록을 다시 읽거나 캐시 스키마 버전을 올린다.

- 기본 테스트: 65개 기록 최초 3페이지 조회 → 버전 동일 시 추가 조회 0회 → 새 기록 추가 시 경계 이후 1회 조회.
- 동시 요청 병합, 같은 시각/나노초 경계, 중간 페이지 실패 복구, 저장소 실패, 계정별 분리, 이력 페이지/재시도 검증.
- 브라우저에서 실제 IndexedDB 복원·새 기록 병합·계정 변경 및 로그아웃 시 삭제 확인.
- Firestore 에뮬레이터에서 거래 매칭·평균 매입가·권한·이벤트·정산 회귀 검증. 실제 사용자 데이터는 테스트하지 않는다.

이는 조회 횟수와 화면 재처리를 줄이는 검증이다. 실제 iPad/갤럭시 탭에서의 로딩 시간 개선률을 측정한 수치는 아니다.

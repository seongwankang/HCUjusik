# GitHub Pages + Firestore Spark 지정가 테스트

현재 실행 구조입니다. Render/Cloudflare/Cloud Functions/서비스 계정 키는 사용하지 않습니다. 기존 Firebase 로그인과 Firestore Web SDK로 지정가 주문을 접수하고 Firestore 트랜잭션으로 체결합니다. 이전 Node 서버 코드는 참고용으로 보존하며 사이트에서 호출하지 않습니다.

## 활성화

1. 최신 **전체 `firestore.rules`**를 Firebase Console → Firestore Database → 규칙에 붙여 넣고 게시합니다. 일괄 `allow write`를 추가하지 않습니다.
2. GitHub Pages 최신 배포에서 새로고침하고 로그인합니다. 주식시장 → 테스트 기업 보기에서 지정가격·수량을 입력합니다.
3. A가 초기 가격 이상으로 주식을 매수합니다. 이후 A가 초기 가격보다 낮은 가격에 일부 매도하고, B가 같은 가격에 매수하면 두 학생 간 체결을 시험할 수 있습니다. 남은 미체결 수량을 취소하면 예약 자산이 반환됩니다.

별도 계정 가입·호스팅 연결·비밀키 등록이 필요하지 않습니다. 기존 `portfolios`, `tradeTests`, `exchangeState` 문서와 자산은 건드리지 않습니다. 새 `sparkAccounts/{uid}` 테스트 계좌는 최초 100만 원으로 한 번만 생성하며 초기화/삭제를 허용하지 않습니다.

## 테스트 범위와 동작

- 두 기업 test-a/test-b, 정수 원/주, 수수료 없음. 종목당 **미체결 최대 4건**입니다. 전체 가격·시간 우선 규칙을 Firestore의 검증 연산 한도 안에서 검사하기 위한 제한입니다. 체결/취소된 주문은 이 4건에 포함되지 않습니다.
- 최초 물량은 기업의 referencePrice/issuedShares로 한 번 설정합니다. 초기 판매 가격 이상인 주문 중 **접수 순번이 먼저인 매수 주문부터** 배분하며, 나중에 더 높은 가격을 써도 초기 배분 순서를 앞지를 수 없습니다.
- 학생 간 거래는 높은 매수가/낮은 매도가 우선, 동일 가격은 접수 순번 우선입니다. 먼저 대기한 반대 주문의 가격으로 부분 체결합니다. 자기 반대 주문과 교차하는 주문은 거부합니다.
- 현금/주식을 주문 시 예약하고 체결·취소 때 해제합니다. 잔액·매도 가능 수량 초과는 규칙에서도 거부합니다. 같은 주문 ID 재전송은 이미 접수된 주문을 반환합니다.
- 접수 순번은 Firestore에서 원자적으로 확정된 주문장 version입니다. 클라이언트 시계와 클릭 시간을 신뢰하지 않습니다.
- 누군가 종목을 열거나 호가 새로고침/주문을 실행할 때 브라우저가 체결 후보를 제안합니다. 모든 브라우저가 닫히면 자동 매칭 작업은 멈추며, 다시 조회하면 처리합니다. 독립 서버처럼 상시 실행되는 구조는 아닙니다.
- 거래정지 중 신규 접수/체결은 거부하지만 취소는 가능합니다. 비활성 계정은 접근/체결이 거부됩니다. 비활성 참가자의 주문이 선두를 막으면 관리자가 종목 화면의 전체 대기 주문에서 취소합니다.
- 200명 행사 전체 주문량을 지원하는 정식 거래소로 간주하지 않습니다. 이 버전은 제한된 두 기업의 테스트용입니다.

## 신뢰 경계와 원자성

브라우저의 계산 결과를 그대로 신뢰하지 않습니다. 공개 주문장 `sparkBooks/{companyId}`의 현재 주문과 다음 상태를 Rules가 비교해, 최선 가격/접수 순번/초기 선착순, 체결 수량, 체결가격을 다시 검증합니다. 최대 4건의 각 주문을 모두 비교합니다. 재고 재발행, 호가 삭제·재정렬에 의한 우선권 조작, 임의 가격 체결은 거부합니다.

한 체결은 주문장, 매수/매도 계좌, 양쪽 주문 상태와 양쪽 체결 기록을 **같은 트랜잭션**으로 기록합니다. `getAfter()`와 version 증가로 필수 동반 쓰기를 검증합니다. 상대방 잔액을 클라이언트가 읽는 대신 `increment()` 변환을 제안하며, Rules가 상대 계좌의 실제 이전/다음 값을 사용해 정확한 자산 변동과 예약 해제를 검증합니다. 잔액이나 주문장을 단독 수정할 수 없습니다. 일부 쓰기 누락 시 전체 체결이 거부됩니다.

`sparkAccounts/{uid}`와 하위 orders/fills 조회는 인증된 소유자만 가능합니다. 관리자도 다른 학생 잔액을 직접 읽는 규칙은 열지 않습니다. 정당한 정산/관리자 취소에 한해서 타인 문서의 제한된 변환 쓰기를 허용합니다. 공개 주문장은 정산 경로를 참조하기 위한 기술적 UID·주문 ID·가격·수량·순번을 포함하므로 참가자는 대기 주문의 UID를 기술적으로 확인할 수 있습니다. 이름/이메일/현금/다른 학생의 비공개 체결 내역은 포함하지 않고, 일반 호가 화면은 가격별 수량 합계만 표시합니다.

기존 활성 참가자/학교 이메일 인증 및 기존 관리자 예외를 그대로 적용합니다. 클라이언트 읽기 쿼리는 본인 하위 컬렉션의 createdAt 정렬, 최대 30건입니다. 별도 복합 인덱스는 필요하지 않습니다. 거래 요청은 일반 Firebase ID 토큰으로 인증되며 Admin SDK 비밀키를 사용하지 않습니다.

## 검증

새 규칙은 제한된 프로토타입입니다. 테스트에서 다음 정상 경로 성공과 공격 거부를 확인했습니다.

- 초기 배분과 부분 체결, 나중의 높은 매수가가 먼저 접수된 초기 구매자를 앞지르지 못함
- 학생 간 가격·시간 우선, 상대방 계좌를 읽지 않고 원자적 정산, 현금/주식 예약·취소
- 주문장이 가득 찬 4건 상태에서 제3의 활성 참가자도 정확한 체결을 제안할 수 있음
- 중복 주문·내용 변경, 동시 예약의 초과 지출, 타인 취소(거부)/관리자 취소(허용)
- 완전한 변조 배치로 더 낮은 매수가 우선 체결, 가짜 체결가격/수량, 현금 1원 추가, 상대 계좌/주문/체결 기록 쓰기 누락을 시도해 거부 확인
- 계좌 단독 증액·타인 계좌 읽기/쓰기·미인증/비활성 접근·초기 재고 재생성·주문장 단독 조작 거부

Firestore emulator demo 프로젝트에서만 검증했습니다. 원격 규칙 게시와 실제 두 계정 체결은 별도 확인해야 합니다. `pnpm test`, 루프백 Firestore emulator의 `pnpm test:rules`, `pnpm build`로 검증합니다. 브라우저 모의 검증도 실제 Firestore emulator와 동일한 새 규칙을 사용합니다.

공식 동작 근거: [원자적 작업과 getAfter](https://firebase.google.com/docs/firestore/manage-data/transactions), [규칙 조건과 접근 한도](https://firebase.google.com/docs/firestore/security/rules-conditions), [목록 비교 연산](https://firebase.google.com/docs/reference/rules/rules.List).

# 경영 이벤트 운영 안내

관리자 → 기업 이벤트에서 발행합니다. 무료 GitHub Pages + Firebase Spark 구조를 유지하며 Cloud Functions나 별도 서버를 추가하지 않습니다. 실제 자동 추첨 대신 관리자가 예고 없이 발행하는 랜덤 이벤트입니다.

## 랜덤 이벤트

대상은 특정 기업 또는 발행 당시 등록된 전체 기업(최대 100개)입니다. 발행 즉시 기업별로 적용합니다. 일매출 변동, 공장/생산 설비/연구 시설의 효율 변동, 설비 파괴, 변화 없음 중 선택합니다. 변동률 -100~500%, 기간 1~2,160시간, 파괴 수량 1~1,000개입니다.

발행 내역의 ‘적용 확인 / 재시도’는 이미 적용된 기업을 건너뜁니다. 정산 중인 기업, 과거 계좌의 매출 분류가 필요한 기업 등은 실패 사유를 표시하며 정산 완료/분류 후 재시도합니다. 전체 기업 적용은 하나의 거대한 트랜잭션이 아닌 기업별 원자 처리입니다. 새로 등록한 기업은 과거 전체 이벤트 대상에 자동 추가하지 않습니다. 기간 시작은 재시도 시간이 아니라 최초 발행 시간입니다.

## 선택형 이벤트

상황, 선택 마감, 선택지 3개와 각각의 비공개 효과를 입력합니다. 발행 당시 전체 기업에 전달됩니다. 사장은 회사경영에서 기업당 한 번 선택하며 변경할 수 없습니다. 미선택 기업은 마감 후 선택할 수 없고 효과도 없습니다. 한 계정이 여러 기업을 운영하면 기업별로 선택합니다.

`events`에는 상황과 선택지 문구만 저장합니다. 비공개 결과는 `eventOutcomes/{eventId}/options/{option}`의 별도 문서입니다. 관리자와 해당 선택을 이미 확정한 담당 사장만 그 선택 결과를 읽습니다. 다른 선택지 결과나 타 기업 적용 효과는 읽을 수 없습니다. 모든 사장이 같은 결과를 골랐을 때 같은 효과가 발생합니다. 다른 기업의 사장이 직접 결과를 알려주는 행위까지 기술적으로 막지는 않습니다.

선택 확정과 결과 적용은 두 단계입니다. 먼저 선택과 회사의 `pendingEvent`를 원자적으로 저장한 뒤, 선택한 결과만 읽어서 효과·설비 변경·적용 영수증을 원자적으로 저장합니다. 완료된 결과는 중복 적용하지 않습니다. 통신 중단 시 ‘결과 적용 / 다시 확인’으로 이어갑니다. 완료 전 다른 선택과 설비 구매는 차단되며, 관리자의 정산은 미적용 선택을 먼저 반영합니다. 따라서 결과를 읽은 뒤 적용 요청을 중단해 손실을 회피할 수 없습니다. 기간은 최초 선택 시점부터입니다. 선택 마감 후에도 이미 저장된 선택의 적용은 복구할 수 있습니다.

## 매출·배당 계산

현재 유효한 이벤트만 정산 시점에 반영합니다. 각 매출 이벤트의 증감액은 기본 매출 × 변동률, 설비 효율 이벤트는 해당 종류의 기본 설비 매출 × 변동률입니다. 정수 원 단위로 각각 0 방향 절삭한 뒤 합산하고 일매출은 최저 0원으로 제한합니다. 예: 기본 10,000원에 -20%와 +10%이면 9,000원입니다. 임시 효과가 기본 매출을 덮어쓰거나 다음 날 복리로 누적되지 않습니다.

설비는 종류별 매출 풀로 관리합니다. 같은 종류의 설비를 일부 파괴하면 보유 수량과 그 종류의 가동/가동 대기 매출을 수량 비율대로 줄입니다(원 단위 내림). 보유량보다 많이 지정하면 보유량까지만 파괴하며 건설비 환급은 없습니다. 파괴 후 다시 건설할 수 있으며 과거 파괴 영수증이 새 설비를 다시 파괴하지 않습니다. 효율 이벤트는 적용 기간 중 해당 종류 전체의 생산 능력에 적용됩니다.

기간 종료는 데이터 삭제나 예약 작업 없이 종료 시각 비교로 처리합니다. 시작 시각 이상, 종료 시각 미만이 적용 범위입니다. 이미 확정된 일일 정산/배당을 나중 이벤트가 소급 변경하지 않습니다. 자동 일일 정산은 없으며 관리자가 기존 일일 정산 버튼을 실행합니다. 이미 정산한 날은 다시 정산하지 않습니다. 정산 중인 기업은 선택/효과 적용/투자가 잠기며 완료 후 재시도합니다. 시장 현재가는 이 효과로 직접 변경하지 않고 기존 체결 가격을 유지합니다.

회사경영은 기본 매출과 이벤트 반영 예상 매출을 구분합니다. 예상치는 화면 조회 시점 기준이며 기간이 지났으면 새로 조회해 확인합니다. 실제 지급액은 정산 스냅샷을 따릅니다.

## 기존 계좌 호환

기존 계좌는 종류별 매출을 저장하지 않고 합계만 저장했습니다. 합계가 0이 아닌 이러한 계좌는 관리자 회사경영의 ‘기존 설비 매출 분류’에서 가동/가동 대기 매출을 각 종류로 나눠 저장해야 추가 투자·설비 파괴·효율 효과를 사용할 수 있습니다. 각 합계는 기존 합계와 정확히 같아야 하며 없는 설비에 매출을 배정할 수 없습니다. 임의로 과거 설비 수익을 추정하거나 현금·수량을 초기화하지 않습니다. 기존 계좌의 일반 매출 이벤트와 일일 정산은 그대로 동작합니다. 새 투자부터 종류별 실제 구매 당시 매출이 기록됩니다.

## 배포·검증

`firestore.rules`를 게시한 후 Pages 최신 빌드를 배포합니다. 신규 경로는 기존 참가자/관리자 역할과 담당 기업 배정을 사용하며 별도 계정·비밀키는 없습니다. 기존 뉴스·회사·학생 데이터를 삭제하지 않습니다. 운영 환경에 테스트 이벤트를 발행하지 않습니다.

`pnpm test`, `pnpm build` 및 루프백 에뮬레이터에서 `FIRESTORE_EMULATOR_HOST=127.0.0.1:8082 node --test --test-concurrency=1 tests/rules/events.test.mjs tests/rules/economy-news.test.mjs tests/rules/news-comments.test.mjs tests/rules/spark-exchange.test.mjs`를 실행합니다. 테스트는 `demo-*` 프로젝트만 사용합니다. 비공개 결과 접근, 역할·기업 격리, 위조 결과/자금/선택 차단, 중복 파괴 방지, 중단 복구, 선택 결과 은폐를 통한 손실 회피 방지, 기간 경계, 정산 매출 반영과 기존 거래·뉴스를 검증합니다.

조회는 Firestore 무료 쿼터를 사용합니다. 효과 이력은 100개씩 끝까지 읽어 계산 누락을 막으므로 이벤트가 매우 많아지면 조회량도 늘어납니다. 발행 후 이벤트/결과를 수정·삭제하는 UI는 제공하지 않습니다.

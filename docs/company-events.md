## 정산 횟수형 효과

새 이벤트는 일매출·설비 효율·투자 비용·배당률 상한의 기간을 `정산 적용 횟수`(1~365회)로 지정합니다. 기업별 실제 정산에 반영된 뒤 한 회 차감하며, 날짜가 지나거나 화면을 열어도 차감하지 않습니다. 정산을 시작해 수익·배당 스냅샷을 확정할 때 회사 `settlementCount`를 한 번 증가시킵니다. 같은 정산의 지급 재시도·복구는 추가 차감하지 않습니다. 선택형 이벤트는 마감 후 선택 결과를 적용한 기업부터 동일하게 계산합니다. 최초로 반영 가능한 다음 정산이 첫 회입니다.

영구 파괴·일회성 자금/직원/설비 지급은 횟수 소진으로 되돌리지 않습니다. 비용 할인은 적용 직후부터 지정 회차 정산까지 유지되고, 그 회차 수익을 고정한 후 원래 가격으로 돌아옵니다. 같은 대상에 새 비용/배당 상한을 적용하면 이전처럼 새 설정이 우선합니다.

새 효과에는 `settlements`, 적용 영수증에는 `startsAfterSettlement`를 저장합니다. 남은 횟수는 `max(0, settlements - (company.settlementCount - startsAfterSettlement))`로 계산합니다. 학생·사장은 카운터나 적용 영수증을 수정할 수 없습니다. 기존 회사는 카운터가 없으면 0부터 시작합니다. 이미 발행된 `hours`형 이벤트는 원래 시간 설정과 기록을 보존하며 새 관리 화면은 횟수형으로만 생성합니다. 선택 마감 시간은 별개로 유지합니다.

아래 기존 시간형 설명은 이전 이벤트 기록의 호환 동작입니다.

> 현재 설비·채용 가격, 순영업수익, R&D 비율 효과는 [경영 정책 v2](business-policy.md)를 따릅니다. 아래 문서의 과거 고정 R&D 일매출 설명은 v2로 대체되었습니다.

# 경영 이벤트 운영 안내

관리자 → 기업 이벤트에서 발행합니다. 무료 GitHub Pages + Firebase Spark 구조를 유지하며 Cloud Functions나 별도 서버를 추가하지 않습니다. 실제 자동 추첨 대신 관리자가 예고 없이 발행하는 랜덤 이벤트입니다.

## 랜덤 이벤트

대상은 선택한 하나 이상의 기업 또는 발행 당시 등록된 전체 기업(최대 100개)입니다. 발행 즉시 기업별로 적용합니다. 일매출 변동, 공장/생산 설비/연구 시설의 효율 변동, 설비 파괴, 변화 없음 중 선택합니다. 변동률 -100~500%, 기간 1~2,160시간, 파괴 수량 1~1,000개입니다.

발행 내역의 ‘적용 확인 / 재시도’는 이미 적용된 기업을 건너뜁니다. 정산 중인 기업, 과거 계좌의 매출 분류가 필요한 기업 등은 실패 사유를 표시하며 정산 완료/분류 후 재시도합니다. 전체 기업 적용은 하나의 거대한 트랜잭션이 아닌 기업별 원자 처리입니다. 새로 등록한 기업은 과거 전체 이벤트 대상에 자동 추가하지 않습니다. 기간 시작은 재시도 시간이 아니라 최초 발행 시간입니다.

## 선택형 이벤트

상황, 선택 마감, 선택지 3개와 각각의 비공개 효과를 입력합니다. 발행 당시 전체 기업에 전달됩니다. 사장은 회사경영에서 기업당 한 번 선택하며 변경할 수 없습니다. 미선택 기업은 마감 후 선택할 수 없고 효과도 없습니다. 한 계정이 여러 기업을 운영하면 기업별로 선택합니다.

`events`에는 상황과 선택지 문구만 저장합니다. 선택이 끝나도 마감 전에는 선택한 효과를 읽거나 적용할 수 없습니다. 관리자 작성 권한을 제외하고, 담당 사장은 마감 후 자기 기업이 선택한 결과만 읽습니다. 적용 완료 결과는 투자자 정보로 공개합니다.

선택은 기업별 한 번 저장하며 여러 진행 중 이벤트도 각각 선택할 수 있습니다. 마감 전에는 설비 투자와 정상 정산을 계속할 수 있고 아직 선택한 효과는 반영하지 않습니다. 마감 후 서버 작업이 저장된 선택의 효과·설비 변경·영수증을 원자적으로 기록합니다. 미선택 기업에는 효과가 없습니다. 기간 효과는 최초 선택 시간이 아닌 마감 시각부터 계산합니다. 이미 적용된 과거 영수증은 유지합니다.

기존 GitHub 작업이 15분 간격으로 마감 큐를 처리합니다. GitHub 지연 때문에 마감 정각의 처리를 보장하지 않습니다. 관리자는 발행 내역의 ‘마감 결과 적용 / 재시도’로 처리할 수도 있습니다. 중복 실행해도 두 번 적용하지 않으며 잠긴 회사는 기존 정산 복구 후 재시도합니다. 수동 새 정산도 마감된 선택 효과를 먼저 반영합니다. 이 큐는 공개 마감 시각만 보관하며 효과·계정 정보는 담지 않습니다.

이벤트 등록의 `함께 올릴 뉴스`에서 관리자가 뉴스 제목과 본문을 직접 작성합니다. 이벤트 상황 설명을 기사로 자동 작성하지 않습니다. 함께 등록을 끄면 이벤트만 발행합니다. 랜덤 이벤트의 기사는 발동·적용 시 뉴스 분류 `이벤트`로 게시하며, 선택형 기사는 마감 후 게시합니다. 뉴스 하단에는 선택지별 효과, 선택한 기업, 실제 반영량·적용 상태와 미선택 기업을 표시합니다. 자동 뉴스에도 기존 댓글 기능을 사용할 수 있습니다. 일반 뉴스는 별도로 작성할 수 있습니다.

## 매출·배당 계산

현재 유효한 이벤트만 정산 시점에 반영합니다. 각 매출 이벤트의 증감액은 기본 매출 × 변동률, 설비 효율 이벤트는 해당 종류의 기본 설비 매출 × 변동률입니다. 정수 원 단위로 각각 0 방향 절삭한 뒤 합산하고 일매출은 최저 0원으로 제한합니다. 예: 기본 10,000원에 -20%와 +10%이면 9,000원입니다. 임시 효과가 기본 매출을 덮어쓰거나 다음 날 복리로 누적되지 않습니다.

설비는 종류별 매출 풀로 관리합니다. 같은 종류의 설비를 일부 파괴하면 보유 수량과 그 종류의 가동/가동 대기 매출을 수량 비율대로 줄입니다(원 단위 내림). 보유량보다 많이 지정하면 보유량까지만 파괴하며 건설비 환급은 없습니다. 파괴 후 다시 건설할 수 있으며 과거 파괴 영수증이 새 설비를 다시 파괴하지 않습니다. 효율 이벤트는 적용 기간 중 해당 종류 전체의 생산 능력에 적용됩니다.

기간 종료는 데이터 삭제나 예약 작업 없이 종료 시각 비교로 처리합니다. 시작 시각 이상, 종료 시각 미만이 적용 범위입니다. 이미 확정된 일일 정산/배당을 나중 이벤트가 소급 변경하지 않습니다. 오전 7시 55분 자동 정산을 사용하며 관리자 수동 정산도 가능합니다. 이미 정산한 날은 다시 정산하지 않습니다. 정산 중인 기업은 선택/효과 적용/투자가 잠기며 완료 후 재시도합니다. 시장 현재가는 이 효과로 직접 변경하지 않고 기존 체결 가격을 유지합니다.

회사경영은 기본 매출과 이벤트 반영 예상 매출을 구분합니다. 예상치는 화면 조회 시점 기준이며 기간이 지났으면 새로 조회해 확인합니다. 실제 지급액은 정산 스냅샷을 따릅니다.

## 기존 계좌 호환

기존 계좌는 종류별 매출을 저장하지 않고 합계만 저장했습니다. 합계가 0이 아닌 이러한 계좌는 관리자 회사경영의 ‘기존 설비 매출 분류’에서 가동/가동 대기 매출을 각 종류로 나눠 저장해야 추가 투자·설비 파괴·효율 효과를 사용할 수 있습니다. 각 합계는 기존 합계와 정확히 같아야 하며 없는 설비에 매출을 배정할 수 없습니다. 임의로 과거 설비 수익을 추정하거나 현금·수량을 초기화하지 않습니다. 기존 계좌의 일반 매출 이벤트와 일일 정산은 그대로 동작합니다. 새 투자부터 종류별 실제 구매 당시 매출이 기록됩니다.

## 배포·검증

`firestore.rules`를 게시한 후 Pages 최신 빌드를 배포합니다. 신규 경로는 기존 참가자/관리자 역할과 담당 기업 배정을 사용하며 별도 계정·비밀키는 없습니다. 기존 뉴스·회사·학생 데이터를 삭제하지 않습니다. 운영 환경에 테스트 이벤트를 발행하지 않습니다.

`pnpm test`, `pnpm build` 및 루프백 에뮬레이터에서 `FIRESTORE_EMULATOR_HOST=127.0.0.1:8082 node --test --test-concurrency=1 tests/rules/events.test.mjs tests/rules/economy-news.test.mjs tests/rules/news-comments.test.mjs tests/rules/spark-exchange.test.mjs`를 실행합니다. 테스트는 `demo-*` 프로젝트만 사용합니다. 비공개 결과 접근, 역할·기업 격리, 위조 결과/자금/선택 차단, 중복 파괴 방지, 중단 복구, 선택 결과 은폐를 통한 손실 회피 방지, 기간 경계, 정산 매출 반영과 기존 거래·뉴스를 검증합니다.

조회는 Firestore 무료 쿼터를 사용합니다. 효과 이력은 100개씩 끝까지 읽어 계산 누락을 막으므로 이벤트가 매우 많아지면 조회량도 늘어납니다. 발행 후 이벤트/결과를 수정·삭제하는 UI는 제공하지 않습니다.
## 랜덤 이벤트의 복수 기업 선택

관리자 이벤트 발행 화면에서 ‘선택한 기업만’을 고르고 기업을 여러 개 체크할 수 있습니다. 선택하지 않은 상태에서는 발행할 수 없으며, 전체 적용은 ‘전체 기업’을 명시적으로 고릅니다. 발행 내역에 대상 기업 이름을 표시합니다.

발행 API는 `companyIds` 배열을 받아 중복을 제거하고 실제 등록된 기업인지 확인한 뒤 기존 `targets` 필드에 저장합니다. 빈 배열은 전체 기업으로 해석하지 않습니다. 이전 `companyId` 단일 기업/전체 기업 요청은 호환하며 선택형 이벤트는 기존처럼 전체 기업을 대상으로 합니다. 적용·재시도는 저장된 대상 목록만 순회하고 기업별 기존 영수증으로 중복 반영을 막습니다. 기존 Firestore 규칙과 데이터 형식을 사용하므로 규칙 재게시나 데이터 변경은 필요하지 않습니다.


## 이벤트 결과 뉴스 자동 처리

기사 초안은 `eventNewsDrafts/{eventId}`에 이벤트와 같은 배치로 저장합니다. 초안은 관리자만 단건 조회할 수 있고 사장·학생은 읽을 수 없습니다. 발행 후 초안 수정은 차단합니다. 함께 등록하는 새 이벤트에 `autoNews:true`, `newsDraftRequired:true`를 저장하고 랜덤 발동 또는 선택 마감 시각을 기존 `eventQueue`에 함께 기록합니다. 기존 GitHub Actions의 15분 간격 작업이 브라우저가 닫혀 있어도 처리합니다. GitHub 스케줄 지연에 따라 마감 정각보다 늦게 게시될 수 있습니다. 추가 서버·유료 서비스·계정 연결은 필요하지 않습니다. 이전 이벤트를 소급해 대량 게시하지 않습니다.

뉴스 ID는 이벤트 ID의 결정적 SHA-256 값이므로 재시도해도 중복 기사가 생기지 않습니다. 적용 실패 기업은 `적용 대기`로 게시하고 큐를 유지합니다. 다음 재시도로 성공하면 같은 기사 결과만 갱신하며 최초 게시 시각·수정된 제목/본문은 유지합니다. 영수증에 기록된 실제 지원금·인원·설비 변화를 표시하고 개인 UID·이메일은 뉴스에 포함하지 않습니다. 미선택 기업은 효과를 받지 않는 것으로 구분합니다.

일반 참가자는 뉴스 결과를 작성·수정할 수 없고, 관리자도 선택 마감 전에 이벤트 결과 메타데이터를 게시할 수 없습니다. 자동 기사는 `news` 문서에 `eventId`와 구조화된 `eventSummary`를 보관합니다. 100개 기업의 긴 이름도 본문 5,000자 한도에 잘리지 않도록 하단 결과를 별도 구조로 렌더링합니다.

이전 버전에서 이미 발행된 초안 없는 자동 뉴스 이벤트는 기존 처리 방식으로 마무리합니다. 새 버전의 함께 등록은 빈 제목·본문을 거부하며 작성한 기사를 그대로 게시합니다. 일반 뉴스·공지 작성과 게시 후 기사 수정, 댓글 기능은 유지합니다.

회사 자금 손실은 전액 차감하여 회사 잔액이 음수가 될 수 있습니다(±1조 원 안전 한도). 이후 지원금·주식 판매 대금·유보 수익은 부채를 줄입니다. 잔액 부족 시 신규 투자·채용은 차단하며 설비·직원 수와 개인 계좌 잔액은 음수가 될 수 없습니다. 스파이는 음수 잔액의 대상에서 돈을 가져오지 않으며 보유 스파이 수입은 부채 상환에 반영합니다.
